ТЕХНИЧЕСКОЕ ЗАДАНИЕ
Group Game App

НАЗНАЧЕНИЕ

Разработать кроссплатформенное мобильное приложение для поиска, создания и организации групповых спортивных игр. Основной сценарий MVP — волейбол, но архитектура должна быть универсальной для других видов спорта.

1. ТЕХНОЛОГИЧЕСКИЙ СТЕК

- Mobile: C# / .NET 10 / .NET MAUI

- Backend: ASP.NET Core Web API / .NET 10

- ORM: Entity Framework Core

- Database: PostgreSQL — единственная основная база данных проекта (backend). SQLite не использовать ни на backend, ни как локальную базу данных мобильного клиента.

- Mobile local storage: не использовать отдельную локальную базу данных; токены хранить в SecureStorage, пользовательские настройки — в Preferences, данные получать через API. При необходимости кэш реализовать отдельно без SQLite и только после согласования.

- Authentication: JWT Access Token + Refresh Token

- API: REST/JSON

- Архитектура: разделение Domain / Application / Infrastructure / API / Mobile

- Сервер является Source of Truth; клиентские данные не считаются доверенными.

9. УЧАСТИЕ И WAITLIST

GameParticipant связывает User с конкретной Game.

Статусы:

- Main

- Waitlist

- Cancelled

- Removed

Если Main заполнен:

- пользователь попадает в Waitlist;

- ему назначается QueuePosition;

- очередь FIFO.

Если участник Main отменяет участие:

- первый подходящий пользователь из Waitlist автоматически переводится в Main;

- отправляется уведомление.

Запретить:

- повторное участие одного пользователя;

- участие в отменённой игре;

- участие в завершённой игре.

Историю отмен сохранять.

# 30. ДОПОЛНИТЕЛЬНЫЕ ТРЕБОВАНИЯ ИЗ ИСХОДНОГО ТЗ

## 30.1. Цели и продуктовые принципы

- Запись на игру должна занимать минимум действий; пользователь сразу видит доступность мест и своё положение в очереди.

- Сервер является единственным источником истины для игр, состава, подписок, прав и очереди.

- Поддерживать бесплатное участие в играх; право создавать/организовывать игры определяется Entitlements и тарифными лимитами.

- Система должна учитывать репутацию, посещаемость, отмены, неявки и жалобы.

## 30.2. Жизненный цикл игры

- Draft — черновик; Open — идёт набор; Full — основной состав заполнен, доступна очередь; StartingSoon — скоро начало; InProgress — игра началась; Completed — завершена; Cancelled — отменена.

- Переходы статусов валидируются backend. Клиент не может самостоятельно изменить статус игры.

- При отмене игры закрыть запись, обработать резервную очередь, сохранить историю и уведомить всех участников.

## 30.3. Участие, отмена и резерв

- Стандартный срок самостоятельной отмены — не позднее чем за 3 часа до начала; параметр настраиваемый на уровне системных настроек и/или конкретной игры.

- После дедлайна самостоятельная отмена запрещена. Организатор или администратор могут выполнить исключение с записью причины в историю.

- Если место освободилось близко ко времени начала, применяется отдельное настраиваемое правило: автоматическое продвижение может выполняться до старта; при необходимости участнику даётся ограниченное время на подтверждение.

- Очередь Waitlist работает по FIFO. При одновременных запросах на последнее место backend должен использовать транзакции/блокировки и ограничения БД, чтобы не превысить MaxPlayers.

- Нельзя иметь более одной активной записи на одну игру; история отмен и переходов между Main/Waitlist сохраняется.

## 30.4. Посещаемость и репутация

- После завершения игры организатор отмечает Attended, NoShow или Excused.

- Профиль показывает рейтинг, количество сыгранных и организованных игр, посещаемость, отмены, NoShow и отзывы с соблюдением настроек приватности.

- Оценка 1–5 звёзд и текстовый отзыв необязательны. Оценивать можно только подтверждённого участника после завершения игры; повторная оценка одной и той же пары в рамках игры запрещена.

- Поддержать оценку организатора участниками и оценку игроков организатором. Возможность скрывать оценки до взаимного голосования или в течение 48 часов оставить настраиваемой бизнес-опцией.

## 30.5. Уведомления

- Обязательные in-app уведомления: подтверждение записи, попадание в резерв, продвижение из резерва, изменение/отмена игры, изменение времени/места, напоминания за 24 часа и за 3 часа, запрос оценки после игры, изменение статуса подписки.

- Push/email/SMS каналы должны подключаться через отдельные провайдеры и пользовательские настройки; отсутствие push-провайдера не должно ломать основные сценарии.

## 30.6. Экраны мобильного приложения

- Splash/Onboarding; регистрация/вход/восстановление доступа; главная с ближайшими играми; поиск и фильтры; карточка и детали игры; мои игры; создание/редактирование игры; управление игрой; основной список и резерв; профиль и статистика; рейтинги/отзывы; подписка/тарифы; уведомления; настройки; помощь/правила/политика; создание жалобы.

- Состояния UI должны покрывать загрузку, пустые результаты, ошибки API, отсутствие сети, запрет доступа, истёкшую сессию, отменённую игру и заполненный основной список.

## 30.7. Административная панель

- Включить dashboard, пользователей и роли, подписки/тарифы/entitlements, игры и шаблоны, виды спорта и уровни, города и площадки, жалобы, блокировки, уведомления, статистику, системные настройки и Audit Log.

## 30.8. Нефункциональные требования

- Первая версия интерфейса — на русском языке; архитектура должна поддерживать локализацию.

- Все timestamps хранить в PostgreSQL в UTC; для отображения использовать часовой пояс пользователя или игры, указанный явно.

- API должен поддерживать пагинацию, сортировку и серверную фильтрацию; критические операции должны быть идемпотентными там, где это применимо.

- Настроить резервное копирование PostgreSQL, мониторинг ошибок и производительности, структурированные логи и health checks.

- Покрыть тестами бизнес-логику очереди, гонки при записи на последнее место, отмены, entitlement-проверки, повторяющиеся игры, посещаемость и рейтинги.

## 30.9. Границы MVP и последующие этапы

- MVP включает регистрацию/авторизацию, профиль, виды спорта и уровни, создание и поиск игр, шаблоны повторяющихся игр, Main/Waitlist с FIFO-продвижением, отмену, уведомления, посещаемость, рейтинги/отзывы, личный blacklist, жалобы, базовую админ-панель и модель подписок/entitlements без обязательного запуска платежей.

- Следующие этапы могут включать реальные платежи, вход Google/Apple, карты и геопоиск, чат, приватные игры, команды/турниры, промокоды и расширенную статистику.

## 30.10. Решения, которые ИИ-разработчик не должен принимать молча

- Если детали не заданы, использовать разумное значение по умолчанию и документировать его. Архитектурно значимые или финансово значимые решения вынести в список вопросов, предложить варианты и дождаться подтверждения до необратимой реализации.

- Оставшиеся бизнес-вопросы: ручное подтверждение участников организатором; передача места другому человеку; оплата самой игры отдельно от подписки; точные лимиты тарифов; приватные игры по ссылке/коду; встроенный чат; карты площадок; правила состава для разных видов спорта.

# 31. ОБЯЗАТЕЛЬНЫЕ ПРАВИЛА ДЛЯ ИИ, КОТОРЫЙ СОЗДАЁТ BACKEND И FRONTEND

1. Сначала проанализировать весь документ и составить краткий план реализации, перечень допущений и открытых вопросов.

1. Создать отдельные проекты backend и frontend в одном репозитории: GroupGame.Domain, GroupGame.Application, GroupGame.Infrastructure, GroupGame.Api, GroupGame.Mobile; административный frontend выделить отдельно, если для него выбран отдельный UI-стек.

1. PostgreSQL — единственная база данных проекта. Не создавать SQLite-файл, локальную SQLite-базу или альтернативную базу данных без прямого согласования.

1. Сначала реализовать схему PostgreSQL, EF Core entities/configurations, индексы, ограничения, миграции и тестовые данные; затем API-контракты, авторизацию и бизнес-сервисы; затем мобильный UI и административный frontend.

1. Согласовать API-контракты DTO, валидацию, форматы ошибок ProblemDetails, пагинацию и правила авторизации между frontend и backend.

1. Не оставлять фальшивые кнопки, фиктивные данные или незавершённые заглушки без явной пометки TODO. Для каждой функции предоставить полный код, список файлов, настройки запуска и тесты.

1. В конце каждого этапа предоставить инструкции запуска backend, подключения к PostgreSQL, применения миграций и запуска frontend; секреты и строки подключения хранить в environment variables/secrets, а не в репозитории.
